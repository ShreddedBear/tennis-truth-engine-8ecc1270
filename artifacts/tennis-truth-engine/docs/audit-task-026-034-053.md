# Metrics #026, #034, #053 — the "permanently blocked" correction

Status: **all 3 DONE and wired live** — 026 (within-match + cross-match), 034
(partial, component-level), 053 (partial, extended).

## The prior claim, and why it was wrong

`docs/audit-task-020-026-034-036-045-052-053.md` reported 026/034/053 as
"BLOCKED, not implemented," on the premise that no code anywhere in this
repository aggregates the approved BSD point-by-point data into a
chronological, per-player, game/point-level series. That premise was false.
`src/lib/pbp-score-state-recovery.ts`'s `reconstructPbpScoreState()` was
**already** replaying every approved-PBP-covered match game-by-game — server,
per-game winner, chronological points, break points faced/saved, deuce
points, point-win streaks — for every match the four `bsd-*-pbp.server.ts`
fetchers cover. The substrate existed; it simply had not been used for these
three codes yet, and in 053's case, a value it already computed was being
silently thrown away by a downstream allowlist gap (see below). This doc
corrects that record and documents what was actually built.

## 1. The 053 allowlist gap (cheap, immediate win)

`pbp-score-state-recovery.ts` already had `add("053", "PARTIAL", ...)` —
pressure-point win rate — before this task started. But three of the four
`bsd-*-pbp.server.ts` fetchers (`bsd-atp-main-pbp.server.ts`,
`bsd-atp-challenger-pbp.server.ts`, `bsd-wta-main-pbp.server.ts`) each build
their live packet through a local `PBP_CODES` allowlist that filters which
derived codes are ever surfaced — and none of the three ever named `"053"`,
so this already-computed value was silently dropped on every request.
`deterministic-pbp-metrics.server.ts`'s own `SUPPORTED` gate had the same
gap one layer downstream — even after fixing the fetcher allowlists, this
second gate would have dropped 053 (and would-be-added 034) again. Both
gaps are fixed:

- `bsd-atp-main-pbp.server.ts`, `bsd-atp-challenger-pbp.server.ts`,
  `bsd-wta-main-pbp.server.ts`: `PBP_CODES` now includes `"034"` and
  `"053"`.
- `deterministic-pbp-metrics.server.ts`: `SUPPORTED` now includes `"034"`
  and `"053"`.

Regression guard: `src/lib/bsd-pbp-code-allowlist.test.ts` asserts the
literal allowlist Set in each of the three files names both codes, and that
`bsd-wta-challenger-pbp.server.ts` (see below) deliberately does not.

### bsd-wta-challenger-pbp.server.ts — verified, not assumed, structurally different

This fourth lane never calls `reconstructPbpScoreState()` at all. Its own
`APPROVED_INDEX` rows (`data/metrics/pbp/wta_challenger/approved-index.jsonl`)
carry only aggregate `set_scores`/`total_points`/`total_games`/`breaks` per
match — no per-game server/point-winner sequence — and are marked
`task18b_raw_fields_available: false` /
`server_oriented_point_chronology_preserved: false` in the observation
provenance this file itself already writes. This was confirmed by reading
the file directly, not inferred from the prior pass's blanket claim.
Consequently 026/034/053 are **structurally** `NOT_ENOUGH_DATA` on the WTA
Challenger lane specifically — documented in that file with a comment
explaining exactly why, and in `audit-metric-026-early-warning-slow-start.ts`
with the same verified reasoning for 026's cross-match path.

## 2. #053 — Pressure & Clean-Game Metrics — extended

`public/seed/metrics.txt` #53 names 6 sub-components. Before this task: only
*Pressure Accumulation Score* (as a match-wide pressure-point win-rate
proxy) was computed. Now:

- **Pressure Accumulation Score** — kept the existing match-wide
  pressure-point win-rate (`pressure_index_pct`), and added a second field
  closer to the bullet's literal wording ("consecutive return games in
  which a player reaches 30-all, deuce, or break point"):
  `pressure_return_games_reached` / `pressure_return_game_longest_streak`,
  replayed per side across only that side's own return games in
  chronological order (a gap where the side instead served does not break
  the streak).
- **Serve Escape Dependency** (`serve_escape_dependency_pct`) — holds that
  required saving a break point, over all non-tiebreak holds.
- **Clean-Hold Rate** (`clean_hold_pct`) — service games held without ever
  reaching deuce or facing a break point.
- **Clean-Break Rate** (`clean_break_pct`) — breaks achieved without the
  return game ever reaching deuce.
- **Love/15 Hold Rate** (`love_fifteen_hold_pct`) — service games held
  while conceding 0 or 1 points.
- **Return-Game Abandonment Rate** — **intentionally still excluded.**
  Distinguishing a returner who "generates no further pressure ... after
  falling behind early" from one who simply lost points normally against a
  strong server requires an intent judgment score state alone cannot make;
  forcing a definition (e.g. "lost the return game 0-1") would conflate
  routine holds against a dominant server with genuine abandonment. Excluded
  rather than guessed, the same convention `032`'s own excluded
  sub-components already use.

All four new hold/break rates are denominated over **non-tiebreak**
service/return games only (`nt_holds`/`nt_breaks`), since deuce/break-point
are not meaningful concepts inside a tiebreak's own separate scoring.
Treatment stays `PARTIAL` (one sub-component, return-game abandonment,
remains unshipped by design).

## 3. #034 — Scoreline Deception Index — new, partial

`public/seed/metrics.txt` #34 names 5 sub-components. All 5 now get a real,
deterministic component from the same match replay:

- **Scoreline vs Point Dominance** — `total_points_won`/`total_points_won_pct`
  alongside `actual_games_won` (already on 002/003), for direct comparison.
- **Scoreline vs Expected Games** — `expected_games_won`, computed from a
  documented, verifiable, **exact** finite-Markov-chain probability model
  (`gameWinProbFromPointProb` in `pbp-score-state-recovery.ts`): given each
  side's own observed service-/return-point win rate this match, what
  fraction of a standard win-by-two game they'd be expected to win if points
  were i.i.d. Bernoulli trials at that rate. This is a standard, textbook
  technique (verified numerically against the known p=0.6 → ~73.6% game-win
  table value), **not** an official catalog formula — documented as such,
  never claimed otherwise. `actual_games_won` is reported alongside it.
- **Scoreline vs Break Opportunities** — `break_chances`/
  `break_points_converted`, the same underlying tallies metric 032's own
  "break opportunities per successful break" bullet already uses. Both 032
  and 034 independently name break-opportunity data in their own real
  catalog bullets, so crediting the same raw counts to both is correct, not
  a repeat of the 004/037 duplicate-crediting bug this file's header
  documents.
- **Scoreline vs Dominance Ratio** — `dominance_ratio`, computed with the
  **same formula** `matchup-efficiency.server.ts`'s canonical master
  Dominance Ratio already uses (own return-points-won% ÷ opponent
  return-points-won%) — reused, not reinvented, and only possible here
  because a single PBP payload already contains both sides' return-point
  totals from the same match.
- **Clutch-Performance Dependency** — `clutch_dependency_gap`
  (pressure-point win rate minus overall point-win rate): a large positive
  gap means the scoreline leaned on outperforming specifically on
  break-point/deuce/tiebreak points.

**No fused "Scoreline Deception Index" number is computed.** No official
fusion formula for that composite exists anywhere in this codebase (see
`reconstruction/specs.ts`'s own "Dominance Ratio is intentionally NOT
reconstructed [here]" precedent for the same discipline applied to a
different composite). Treatment stays `PARTIAL`: components, not a
fabricated index.

## 4. #026 — Early-Warning / Slow-Start Metrics — new, two layers

The user's own plain-language framing: *"a decent player starting slow —
calculated by looking at their previous matches, seeing if they start
scoring slow, and end up winning the match anyway, on multiple occasions."*
That is genuinely two different pieces of work, both now shipped:

### (a) Within-match detector — `deriveOpeningWindowProfile()`

New sibling function in `pbp-score-state-recovery.ts` (reuses the same
`collectGames`/`gameWinner` replay `reconstructPbpScoreState` uses). Per
side, per match:

- `opening_service_game_held`, `opening_return_game_broken` — that side's
  own first service/return game specifically (found by scanning in order,
  not assumed to be game index 0/1).
- `first_4_games_win_differential`, `first_6_games_point_differential` —
  over the match's actual first 4/6 games.
- `early_break_conceded` — broken in either of the side's own first two
  service games.
- `time_to_first_break_games` — 1-based index of the match's first break,
  whoever's serve.
- `slow_start_flag` — **this build's own explicit, documented threshold**:
  down 2+ games after the first four (`first_4_games_win_differential <=
  -2`). No official numeric threshold exists in the catalog for the "Set-1
  Slow-Start Index" composite; this one is directional (a definite bad
  start, not a marginal 2-2 split) and computable from any match with ≥4
  games. Not shipped: Set-1 Slow-Start Index as a continuous composite
  score, First-Set Recovery After Early Break (needs full first-set outcome
  tracking this sibling function does not replay), and the three
  shot-level/serve-number bullets (Early-Error Rate, Early First-Serve
  Efficiency, Early Return Pressure) — same gap `016`'s own PARTIAL
  treatment already documents.

### (b) Cross-match aggregation — `computeSlowStartRecovery()`

New module `audit-metric-026-early-warning-slow-start.ts`. For a player's
own past matches that ALSO have usable BSD PBP coverage (cross-referenced
against the same `results.json` index files each `bsd-*-pbp.server.ts`
fetcher reads — never assumed), what fraction of slow-start-flagged matches
still ended in a win. Match-outcome ground truth is taken from
`laneMatchesBefore`'s own already-validated match history
(`task18c-rank-form-workload.ts`), cross-referenced to each PBP-covered
candidate by date + normalized opponent identity — the same technique
`audit-metric-046-match-state-elo.ts`'s `buildSetScoreIndex` already uses —
rather than re-deriving the match winner from PBP a second time.

**Minimum-support threshold, explicitly reasoned:** `audit-metrics-shared.ts`'s
`MIN_SUPPORT_N=50` convention is calibrated against the full four-tour
static results/schedule history (thousands of matches per active player),
which BSD approved PBP coverage does not remotely approach — coverage only
starts 2024-01-01 (ATP Main) / 2024-12-02 (WTA Main) / 2025-01-01 (ATP
Challenger). Requiring 50 slow-start instances would make this aggregate
permanently `NOT_ENOUGH_DATA` for every player, which is itself a form of
dishonesty. This module instead uses `MIN_SLOW_START_INSTANCES=5` (the
smallest count this build is willing to call a "rate" rather than an
anecdote) and an independent `MIN_MATCHES_EXAMINED=6` floor on total
PBP-covered matches examined. Below either, `NOT_ENOUGH_DATA` is reported
with the real counts, never a rounded-up or guessed rate.

**WTA_CHALLENGER**: `NOT_ENOUGH_DATA`, structural, same verified reason as
053 above.

### Wiring

`deterministic-batch3-early-warning.server.ts` adapts
`computeSlowStartRecovery`'s `LaneOutcome` into this app's `MetricFinding`
shape. Unlike the batch1/batch2 modules (pure replays over the in-memory
static index), 026's cross-match aggregation makes real live BSD PBP fetches
for a player's own past matches — the same cost profile as the four
`bsd-*-pbp.server.ts` context builders — so it is tried in
`warehouse-first-researcher.server.ts`'s live-fetch tier (alongside those
builders), not the cheap deterministic chain ahead of it.

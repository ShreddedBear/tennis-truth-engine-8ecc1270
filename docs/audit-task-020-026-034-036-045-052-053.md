## #020 — Level/Tour Transition — DONE

File: `src/lib/audit-metric-020-level-tour-transition.ts` (+ `.test.ts`,
`.leakage.test.ts`). Wired via `deterministic-batch2-new-metrics.server.ts`.

**historical-results-recovery.ts retargeting.** The old "020" case in that
file computed a trailing-90-day win record banded by opponent rank/Elo
quality. Read carefully against the full evidence-gap.ts catalog (not
guessed from name similarity), that computation is an exact bullet match
for real code **006** ("Opponent-Adjusted Strength of Schedule": "recent
opponent strength", "comparable-strength results") — it reads no
tournament-level or event data at all, so it never actually satisfied 020's
real "Level/Tour Transition" definition. Retargeted to 006, freeing 020 for
this fresh build. See the dedicated commit and the long comment on
`TASK18A_HISTORICAL_RESULTS_CODES` in `historical-results-recovery.ts`.

**Shipped bullets:**
- *Performance vs Opponent Elo Differential* — win rate binned into four
  pre-match derived-Elo-gap bands (favorite-strong ≥100, favorite-slight
  0-100, underdog-slight 0 to -100, underdog-strong ≤-100). Uses Elo, not
  ranking bands, per the catalog's own explicit instruction ("rather than
  ranking bands") — same substitution `#031`/`#041` already made for the
  same reason (rank is sparse/absent exactly where it always is; Elo
  replays from raw results in every lane).
- *Post-Strong/Weak-Tournament Performance* — groups a player's own
  chronological matches into tournament "runs" (maximal consecutive
  same-tournament sequences); classifies each run STRONG (≥50% win rate) or
  WEAK; reports this player's win rate in matches immediately following a
  STRONG vs. a WEAK prior run. A direct, honest regression-to-the-mean
  check computed only from real realized results.

**Not shipped (BLOCKED):** *Tour-Level Transition Performance* (moving
between ITF→Challenger→ATP/WTA or qualifying→main-draw) needs merging a
player's identity across two *separate* static-index lane dictionaries
(e.g. `ATP_MAIN` and `ATP_CHALLENGER`) ordered by date to detect a level
switch — a materially larger cross-lane plumbing task than any other module
in this batch attempts. Not approximated; documented here so it isn't
silently forgotten.

**Lane coverage:** all four lanes (neither shipped bullet needs
`set_scores`).

## #036 — Loss Autopsy Metrics — DONE

File: `src/lib/audit-metric-036-loss-autopsy.ts` (+ `.test.ts`,
`.leakage.test.ts`). Wired via `deterministic-batch2-new-metrics.server.ts`.

**Important correction to this task's own brief.**
`audit-metric-036-037-039-live.server.ts` (+
`audit-metric-036-037-loss-win-autopsy.ts`) is **not** "a self-audit of the
app's own win-probability calibration across the whole DB" as this task's
brief assumed — there is no calibration-bucket/reliability content in it at
all, and it has no relationship to `calibration.ts`/
`calibration-matrix-autofill.ts` (confirmed by direct inspection and
repo-wide search). What it actually is: a *whole-population* classifier —
it aggregates **every** TennisMatrixAi-scored match in the audit DB into a
single shared win/loss-category distribution
(`summarizeAutopsyDistribution`). That is still the wrong shape for
`evidence-gap.ts`'s per-player 036 definition: a single DB-wide number
cannot supply an independent `p1_value`/`p2_value` pair for a specific
p1-vs-p2 audit request, whichever way you slice it. So the brief's
conclusion (build a separate per-player 036, leave that file alone) was
still correct, just for a more precise reason than originally stated. Added
a corrected header comment to `audit-metric-036-037-039-live.server.ts`
pointing at this doc and at the real per-player module, so a future reader
does not conflate the two again.

**Shipped bullets** (real chronological loss history, replayed from the
static index the same way `#027`/`#031`/`#041`/`#045`/`#046` already do):
- *Loss Favorite Status* — was the player the pre-match Elo favorite going
  into each loss (all four lanes).
- *Loss Opponent Quality* — opponent's pre-match derived Elo (all four
  lanes).
- *Loss Surface* (all four lanes).
- *Lost Set 1* / *Loss in Deciding Set* / *Loss in Tiebreak* /
  *Competitive vs Blowout Loss* — derived from `set_scores`, restricted to
  `WTA_MAIN`/`ATP_CHALLENGER` (reported `null`, never guessed, on the other
  two lanes).
- *Bad-Loss Severity Index* — a composite defined here as the average Elo
  gap by which the player was favored across their trailing losses (0 floor
  for underdog losses). A transparent, reproducible severity proxy built
  only from the favorite/opponent-quality signal this module can actually
  support, not a fabricated multi-factor score.

**Not shipped (BLOCKED):** Loss Point Differential, Loss Break
Differential, Loss Serve Deterioration, Loss Return Deterioration, Loss
Physical Problem, Loss Match Length — none of this exists anywhere in the
static history index or in any per-historical-match aggregation of the
approved BSD PBP data. *Lost After Leading* is also not shipped: `set_scores`
gives only the final per-set score, never whether the player held a
mid-match lead before losing it.

**Lane coverage:** GO on all four lanes for the core bullets; the four
`set_scores`-derived fields are `null` outside `WTA_MAIN`/`ATP_CHALLENGER`.

## #052 — Entropy & Lead Durability — DONE

File: `src/lib/audit-metric-052-entropy-lead-durability.ts` (+ `.test.ts`,
`.leakage.test.ts`). Wired via `deterministic-batch2-new-metrics.server.ts`.

**Documented granularity substitution.** The catalog defines Set-Score/
Game-Score Entropy as "how concentrated or spread out the range of
*plausible* final scorelines is *for a given win probability*" — a
forward-looking, win-probability-conditioned model output. This module
instead computes the Shannon entropy (bits) of the player's own **realized**
historical set-score / total-games-per-set distribution as of `asOfDate` —
an empirical proxy for the same underlying idea (how varied vs. how
concentrated this player's actual scorelines tend to be), not the
win-probability-conditioned model the catalog describes. Documented here
and in the module header, not hidden, per this project's established
convention for this kind of substitution (see `#031`'s header).

**Not shipped (BLOCKED):** Lead Durability Index, Deficit Survivability
Index, Double-Break Creation/Surrender Rate, Rebreak-Window Probability, and
Break Clustering all need in-match break/lead-state sequence data — none of
which exists in the static index (final set scores only, no break events).

**Lane coverage:** `WTA_MAIN`/`ATP_CHALLENGER` only (`set_scores`
dependency).

## #026 — Early-Warning / Slow-Start Metrics — CORRECTED: not blocked, now DONE

> **This section's original conclusion below was wrong.** See the correction
> note at the top of this doc and `docs/audit-task-026-034-053.md` for what
> was actually built and wired. Kept verbatim below for the historical
> record of how the earlier (incorrect) "BLOCKED" finding was reached.

All eleven bullets (opening service-game hold%, opening return-game break%,
first-four/first-six-games differentials, early break-conceded frequency,
time-to-first-break, set-1 slow-start index, first-set recovery after early
break, early-error rate, early first-serve efficiency, early return
pressure, warm-up dependency index, sustainable break score) require
knowing the **order** games/points were played within a match. The static
history index this batch's modules read from carries only match-level
results and, on two lanes, a set's *final* score — never in-set game order.
The approved BSD PBP integration (`bsd-*-pbp.server.ts`) does carry genuine
point-by-point sequence in principle, but no code in this repository
aggregates it into a first-N-games-scoped, chronological per-player series
the way `audit-metric-046-match-state-elo.ts` replays set-level results —
`metric-source-family-policy.ts`'s own long-standing comment on `PBP_METRICS`
already reached this same conclusion ("needs a first-N-games-scoped replay
this engine does not yet build"). Building that aggregation is a materially
larger undertaking than any other module in this batch and was not
attempted here. `metric-classification.ts` already has a regression test
(`metric-classification.test.ts`, "does not classify known-recoverable
metrics as excluded") explicitly guarding 026 against being marked
`PROTECTED_UNAVAILABLE` — respected here: this is "not yet built," not
"structurally impossible," so no classification-registry change was made.

## #034 — Scoreline Deception Index — CORRECTED: not blocked, now DONE (partial)

> **This section's original conclusion below was wrong.** See the correction
> note at the top of this doc and `docs/audit-task-026-034-053.md` for what
> was actually built and wired. Kept verbatim below for the historical
> record of how the earlier (incorrect) "BLOCKED" finding was reached.

All five bullets (scoreline vs. point dominance/expected games/break
opportunities/Dominance Ratio, and clutch-performance dependency) require
total points won and/or break-opportunity counts per historical match. The
static index carries none of this at all (final set/match results only,
plus per-set game totals on two lanes); no code in this repository
aggregates the approved BSD PBP data into per-historical-match points-won/
break-opportunity/Dominance-Ratio figures outside the narrow, differently-
scoped `audit-metric-036-037-039-live.server.ts` population report.
Approximating any bullet from final scorelines alone (e.g. treating a
lopsided set score as a stand-in for point dominance) would not measure
what the metric actually defines, so it was deliberately not done.

## What actually unblocked #026/#034/#053

The missing capability this section originally called for turned out to
already exist: `src/lib/pbp-score-state-recovery.ts`'s
`reconstructPbpScoreState()` already replays the approved BSD PBP payload
into a chronological, per-player, game/point-level series for any match the
four `bsd-*-pbp.server.ts` fetchers cover. `docs/audit-task-026-034-053.md`
is the write-up of the actual fix: a `PBP_CODES` allowlist gap that was
silently dropping 053 (already computed) and, once added, 034 from every
live packet in three of the four fetcher files; new `add("034",...)` and
extended `add("053",...)` reconstruction in `pbp-score-state-recovery.ts`;
a new sibling function `deriveOpeningWindowProfile()` in that same file for
026's within-match detector; and a new standalone module
(`audit-metric-026-early-warning-slow-start.ts`) for 026's cross-match
slow-start-recovery aggregation, wired via
`deterministic-batch3-early-warning.server.ts`. See that doc for full
details, per-lane coverage, and what remains intentionally excluded within
each of the three codes.

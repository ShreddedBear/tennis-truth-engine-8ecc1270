# Metrics 038, 040, 062 — re-verified against real source data and built

A prior audit pass reported 022, 038, 040, 062, and 070 as structurally UNAVAILABLE. That
was re-checked directly against every raw source file in this repository (not assumed) as
part of resolving this task. The verdict split:

- **022 Serve/Return Shot-Level Efficiency** — confirmed genuinely UNAVAILABLE. No CSV or
  live provider anywhere in this repository carries shot placement, rally direction, or
  court-position data. No change made.
- **070 Support Team/Prep** — confirmed genuinely UNAVAILABLE for its real ask. The catalog
  wording ("the effect of receiving a walkover into the current round") is about the
  CURRENT tournament's live draw state, which the static history index (a record of past
  matches) cannot supply regardless of what data it contains — this needs live/current
  draw context from the audited match's own metadata, not historical stats. (An earlier,
  looser read of this task considered `status_extra: WALKOVER` — already ingested for
  WTA_MAIN — a possible partial fix; on closer reading that field answers "was a PAST match
  a walkover," not "did this player already receive a walkover earlier in the CURRENT
  draw," so it does not actually address 070's real ask. No change made.)
- **038, 040, 062** — all three had a real, previously-missed data path. Built below.

## 038 — Opponent-Adjusted Residual Performance

Real per-player games/sets-won% compared against an Elo-band population cohort (other
players within ±100 Elo, pooled across their own matches), computed from set_scores already
in the static index. Hold%, break%, Dominance Ratio, and serve/return-points residuals are
explicitly NOT computed — a genuine "opponent-specific" cohort (same catalog wording) would
need PBP coverage on a population of other players' matches against the same opponent,
which is far too sparse to support reliably. Documented compromise, not a silent narrowing.

GO on WTA_MAIN and ATP_CHALLENGER only (the two lanes with broad set_scores coverage).

`src/lib/audit-metric-038-opponent-adjusted-residual-performance.ts`, wired via
`deterministic-batch6-residual-decline-stakes.server.ts`.

## 040 — Hidden Decline Detector

Cross-match trend (earlier half vs. recent half of a player's own BSD-approved PBP-covered
matches) on ace rate, double-fault rate, overall service-points-won%, return-points-won%,
hold% (the "service-game danger-score/hold-vulnerability" proxy), and break-points-converted%.
Each dimension is tested with the same two-proportion confidence-interval method metric 047
already established (`twoProportionZTest`, reused directly) — a verdict of DECLINE requires
both a lower recent-half rate AND a 95% CI on the difference that excludes zero, never a raw
delta alone.

Explicitly excluded, each for a specific verified reason: serve velocity (no source
anywhere carries it), first/second-serve-split trends (the raw PBP payload has no
serve-number field — `reconstructPbpScoreState` itself documents `serve_number_available:
false`), match duration trend (no duration field in the PBP replay), three-set-dependency
trend (no reliable derivation was available in this pass's scope).

GO on ATP_MAIN, ATP_CHALLENGER, WTA_MAIN (matches 026's own PBP-lane eligibility);
WTA_CHALLENGER excluded — its approved index has no per-game chronology, same reason 026
excludes it.

`src/lib/audit-metric-040-hidden-decline-detector.ts`, wired via the same batch6 file's
live-fetch tier (same phase as 026's own live-fetch tier — needs a live BSD PBP call, not
just the static index).

## 062 — Motivation / Stakes

A prior pass called this fully BLOCKED, citing a "confirmed schema gap on both
ranking-points-defended and draw/seed/bye metadata." That was checked against the live
48-table Supabase schema, which genuinely lacks these columns — but never checked this
repository's raw static-index source CSVs. `winner_seed`, `loser_seed`, `draw_size`,
`winner_rank_points`, and `loser_rank_points` are real columns in the TennisMyLife ATP
Challenger normalized CSVs (`data/public/tennismylife-challenger/normalized/*.csv`) — they
were simply never carried through `scripts/build-runtime-tennis-index.mjs`'s
`compactDetails()` into the runtime index. That gap is now fixed: `compactDetails()` (and
`reverseDetails()`, for the loser's own reversed perspective) capture
`self_seed`/`opponent_seed`/`draw_size`/`self_rank_points`/`opponent_rank_points` for the
ATP_CHALLENGER (`orientation==='WINNER'`) ingestion path.

Verified present in the rebuilt index: ~30% of ATP_CHALLENGER rows carry a populated
`self_seed` (consistent with only seeded players in each draw actually having a seed),
`draw_size` populated on effectively every row from this source.

Scope, stated honestly: this data exists ONLY for ATP_CHALLENGER — ATP_MAIN
(`predixsport/atp/atp_elo_matches.csv`), WTA_MAIN (`tennisdata-wta-main`), and
WTA_CHALLENGER (`production-history/wta_challenger`) do not carry these columns at all,
verified directly against each source file's own header row. "Ranking points defended" in
the strict sense (this year's points at stake vs. what rolls off from the same tournament
last year) is NOT computed — no reliable same-tournament year-over-year match exists in
this pass's scope. What ships is a real, narrower "stakes profile": seeded-rate%, average
seed when seeded, and average ranking points at stake, over a player's own past
ATP_CHALLENGER matches. "Public milestone context" is not attempted at all — it needs
event-level narrative context no static index can supply.

`src/lib/audit-metric-062-motivation-stakes.ts`, wired via the same batch6 file's
synchronous tier (038/062 share a tier since both are static-index-only, no live fetch).

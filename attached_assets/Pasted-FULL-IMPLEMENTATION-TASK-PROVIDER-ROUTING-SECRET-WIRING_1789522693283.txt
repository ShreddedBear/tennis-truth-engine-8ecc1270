==================================================

Do not blindly force Live_Tennis_Api for endpoints/data that it does not support.

Instead implement capability-aware routing:

IF Live_Tennis_Api supports the requested operation:
    use Live_Tennis_Api

Then:

API-Tennis

    ↓
historical DB

Do NOT stop at the first provider merely because its API key exists.

3. FIX THE CURRENT COMPOSITE PROVIDER BUG
==================================================

Inspect the existing provider factory carefully.

There is currently a dangerous pattern where CompositeTennisProvider can depend on X_RAPIDAPI_KEY being present before the composite/fallback architecture is created.

Fix this.

The existence of X_RAPIDAPI_KEY must NOT determine whether historical DB fallback is available.

Example:

BAD:

    create CompositeTennisProvider(...)
} else {
    return apiTennisProvider
}

GOOD:

create the resilient/composite provider regardless of whether RapidAPI exists.

Optional providers should simply be unavailable when their key is missing.

The provider chain must still reach:

historical_matches

even when RapidAPI is unavailable.

==================================================

Keep these two concepts explicitly separate:

MODEL PROBABILITY
=
Probability produced by Tennis Matrix prediction engine.

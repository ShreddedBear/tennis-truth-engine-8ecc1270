1. Availability is now the most important technical fix

The audit found that Availability uses wall-clock time during historical replay.

That’s unacceptable for the holdout.

A June 2026 match must only see information that was available before that match, not information that became known in September.

The correct remediation should be something like:

historical replay
     ↓
match cutoff timestamp
     ↓
Availability
     ↓
only evidence ≤ cutoff

And this should be fixed before we even construct the holdout.

Importantly, this isn’t a Candidate D change. It’s a point-in-time correctness fix to the historical evaluation infrastructure.

⸻

2. The identity number needs one small audit correction

The report says:

* 3,723 deterministic matches
* 7,990 unmapped
* 11,714 total

But:

3,723 + 7,990 = 11,713

So there is one player unaccounted for.

That’s probably trivial—e.g. another classification—but because we’re building a historical holdout, I would have Claude reconcile that one-row discrepancy before proceeding.

More importantly, the broad 11,714-player test isn’t necessarily the right final measure.

We don’t need to prove that every player in Live Tennis API maps perfectly.

We need to prove that every player appearing in the eventual holdout maps deterministically.

So the proper sequence is:

Live Tennis population
        ↓
filter to eligible singles matches
        ↓
candidate holdout
        ↓
player identity mapping
        ↓
0 ambiguous / 0 unresolved

If a player can’t be mapped, that match should be excluded from the predeclared gradeability rule, not guessed.

⸻

3. Tournament-level mapping needs the same treatment

Same principle.

Don’t try to solve every tournament in the provider.

For the eventual holdout, we need deterministic mapping of:

Live Tennis tournament
        ↓
canonical tournament
        ↓
canonical level
        ↓
Prediction Engine taxonomy

No guessing.

No “probably ATP 250.”

If a tournament can’t be classified safely, it needs to be marked ungradeable/excluded according to a rule declared before looking at B/D performance.

⸻

4. The 33,357 number is NOT our holdout

This is important.

The audit found:

33,357 rows from June 3–September 20.

That’s evidence that the missing post-June population exists.

But it is not yet an evaluation population, because it contains:

* non-singles
* potentially incomplete records
* unmapped identities
* potentially ambiguous tournament levels
* varying PBP completeness

So we should not call 33,357 our holdout.

Instead:

33,357 observed source rows
          ↓
eligibility rules
          ↓
singles only
          ↓
supported tours/levels
          ↓
valid identities
          ↓
valid surface
          ↓
valid outcome
          ↓
required feature availability
          ↓
point-in-time safe
          ↓
FINAL HOLDOUT

And only then do we fingerprint it.

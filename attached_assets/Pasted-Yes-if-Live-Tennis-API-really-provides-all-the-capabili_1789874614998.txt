The one thing I DON’T want to do

I don’t want Claude to blindly delete MatchStat/API-Tennis because we know you’re no longer paying for them, but we don’t yet know whether Live Tennis API has every endpoint your code currently calls.

For example, if your Prediction Engine asks the provider for:

historical match
→ serve statistics
→ player profile
→ ranking
→ surface
→ tournament metadata
→ H2H

and Live Tennis API only supplies:

fixture
→ score
→ tournament
→ players

then the app may still run, but your predictions silently become thinner. That’s the problem I was trying to prevent.

And that is especially important for your 50% investigation: we don’t want a provider migration accidentally reducing the data going into the model and then mistaking the resulting probability compression for a model problem.

So your goal is absolutely reasonable

You don’t need to keep paying for MatchStat/API-Tennis just because they’re currently wired in.

The correct engineering task is:

Replace MatchStat and API-Tennis with Live Tennis API as the primary provider, preserve the existing internal contracts and Prediction Engine behavior, retain ESPN only as fallback where useful, and verify capability parity before deleting the old providers.

Once we have the Live Tennis API documentation/product identity, we can tell Claude to perform that parity audit. If it passes, then we can safely retire the two services.
